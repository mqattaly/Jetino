# جتینو (Jetino)

پروژهٔ PWA فارسی برای دو سرویس محلی بندر خمیر: **سفارش غذای محلی** و **خرید از سوپرمارکت با لیست متنی** (پیک می‌خرد و می‌آورد). محدودهٔ نسخهٔ اولیه و تصمیم‌های باز در `PRD.md` و `Master_Project_Context.md` ثبت شده‌اند.

## نقشهٔ کد (گراف دانش)

کل کد پروژه به یک گراف قابل پیمایش تبدیل شده است: هر تابع، کامپوننت، جدول دیتابیس و رابطه‌هایشان. نقطهٔ شروع: [`docs/graph/README.md`](docs/graph/README.md) برای راهنما، [`docs/graph/NAGHSHE.md`](docs/graph/NAGHSHE.md) برای خلاصهٔ فارسی معماری، و `docs/graph/graph.html` برای دیدن تعاملی نقشه. بازسازی گراف: `bash scripts/graph/build-graph.sh`.

## اجرای رابط کاربری

```bash
npm install
npm run dev
```

## نصب وب‌اپ و حالت آفلاین

رابط کاربری manifest و service worker دارد و روی HTTPS (یا localhost) از گزینهٔ نصب مرورگر پشتیبانی می‌کند. shell برنامه و فایل‌های buildشده برای بارگذاری مجدد آفلاین cache می‌شوند؛ درخواست‌های API عمداً cache نمی‌شوند، بنابراین ثبت سفارش، ورود و وضعیت‌های زنده در حالت آفلاین در دسترس نیستند. برای نصب در موبایل از منوی مرورگر «افزودن به صفحهٔ اصلی» را انتخاب کنید.

## اجرای API و پایگاه دادهٔ توسعه

```bash
cp .env.example .env
# مقادیر JWT_SECRET و OTP_HMAC_SECRET را برای توسعه با اسرار تصادفی جایگزین کنید.
docker compose up -d postgres
cd api
cp .env.example .env
npm install
npm run db:migrate
npm run db:seed:demo # اختیاری؛ یک رستوران نمونه برای تست رابط مشتری می‌سازد.
npm run dev
```

آزمون‌های واحد با `cd api && npm test` بدون پایگاه داده اجرا می‌شوند. آزمون یکپارچهٔ `src/database/order-flow.integration.spec.ts` جریان واقعی سفارش نقدی (قیمت‌گذاری سرور، تکرار ایمن، آشپزخانه، تخصیص پیک، وصول وجه و تسویه) را روی PostgreSQL اجرا می‌کند و فقط وقتی `DATABASE_URL_TEST` تنظیم باشد از حالت skip خارج می‌شود؛ هر اجرا یک schema موقت می‌سازد و در پایان حذف می‌کند:

```bash
cd api && DATABASE_URL_TEST="postgresql://jetino:jetino_local_only@localhost:5432/jetino?schema=public" npm test
```

همین دستور همراه build فرانت‌اند و API در GitHub Actions (`.github/workflows/ci.yml`) با یک سرویس `postgres:16-alpine` اجرا می‌شود؛ بنابراین SQL مهاجرت‌ها و کوئری‌ها در هر push راستی‌آزمایی می‌شوند، نه فقط پارس متنی.

سلامت API: `GET http://localhost:3000/api/v1/health`

در صورت اجرای فرانت‌اند و API روی originهای متفاوت، `CORS_ORIGIN` باید origin فرانت‌اند باشد. برای ورود OTP، کلید کاوه‌نگار و نام قالب تأیید باید در محیط API تنظیم شود. هیچ کلید واقعی یا مقدار محرمانه‌ای را در فایل‌های نمونه یا Git ذخیره نکنید.

### مقادیر مالی و دسترسی مدیر کل

مقدار شروع کرایهٔ ثابت بندر خمیر ۵۰۰٬۰۰۰ ریال و کمیسیون پیش‌فرض ۱۰٪ است؛ هر دو موقت و قابل تغییر هستند. برای ارتقای کاربری که قبلاً با OTP وارد شده، در `api/.env` مقدار `ADMIN_PHONE` را تنظیم کنید و اجرا کنید:

```bash
npm run admin:promote
```

پس از اعطای نقش، کاربر باید دوباره وارد شود تا JWT جدید نقش مدیر کل را داشته باشد. پنل گرافیکی تنظیم قیمت و بررسی درخواست‌های کسب‌وکار در `/admin/settings` در دسترس است. API گزارش پایهٔ `GET /api/v1/admin/reports/summary?period=24h|7d|30d` فقط برای مدیر کل است و آمار کل/بازهٔ انتخابی، سفارش‌های در انتظار و در مسیر، ارزش سفارش‌ها و وجه نقد وصول‌شده را برمی‌گرداند. APIهای محافظت‌شدهٔ `GET/PATCH /api/v1/admin/settings` و `GET /api/v1/admin/businesses?status=PENDING` و `PATCH /api/v1/admin/businesses/:id/status` فقط با نقش `SUPER_ADMIN` کار می‌کنند. بدنهٔ PATCH نمونه: `{"deliveryFeeRial":600000,"defaultCommissionBps":1200}`. مبالغ ریال و کمیسیون برحسب basis point هستند (۱۰۰۰ = ۱۰٪). تغییرها در audit log ثبت می‌شوند.

پنل مدیر کل علاوه بر تنظیمات، گزارش عملیاتی با بازهٔ زمانی، پایش سفارش‌ها با فیلتر وضعیت و جستجو (`GET /api/v1/admin/orders?status=&search=&limit=25&offset=0`؛ جستجو با شمارهٔ مشتری، نام کسب‌وکار یا ۸ رقم اول کد سفارش، سقف هر صفحه ۱۰۰ سفارش و پاسخ به شکل `{items,totalMatches,limit,offset}`)، تخصیص راننده و بخش تسویهٔ وجه نقد را نشان می‌دهد. هر ردیف سفارش، پیوند `geo:` مختصات تحویل و نشانگر زمان انتظار (برای سفارش‌های بیش از ۱۵ دقیقه در انتظار پاسخ کسب‌وکار، برداشت پیک یا تحویل) را نمایش می‌دهد. `GET /api/v1/admin/reports/business-performance?period=` فروش، کمیسیون، میانگین زمان آماده‌سازی و مبلغ تحویل‌داده‌شدهٔ وصول‌نشده را برای هر کسب‌وکار (حداکثر ۵۰ ردیف) برمی‌گرداند.
`GET /api/v1/admin/reports/cash-outstanding` ماندهٔ وجه هر راننده را می‌دهد و `POST /api/v1/admin/reports/settlements` با بدنهٔ `{"driverId":"…","expectedAmountRial":"5500"}` همهٔ وصول‌های باز آن راننده را در یک تراکنش بسته می‌کند؛ اگر مبلغ با ماندهٔ لحظهٔ ثبت برابر نباشد عملیات رد می‌شود تا وجه جابه‌جا نشود. پرداخت واقعی در خارج از پنل انجام می‌شود و این بخش فقط ثبت و بایگانی آن است. راننده با `GET /api/v1/drivers/me/wallet/cash-summary` مبلغی را که هنوز نزد او مانده و جمع تسویه‌های قبلی خود می‌بیند.

### گزارش عملیات حساس (Audit)

همهٔ تغییرهای مالی، وضعیت و دسترسی در جدول `audit_logs` نوشته می‌شوند و مدیر کل می‌تواند آن‌ها را در پنل `/admin/settings` (بخش «گزارش عملیات حساس») ببیند: `GET /api/v1/admin/audit-logs?action=&actorId=&entityId=&since=&until=&limit=&offset=` و `GET /api/v1/admin/audit-logs/actions` برای فهرست عملیات‌های واقعیِ ثبت‌شده. این مسیر فقط برای `SUPER_ADMIN` باز است، شمارهٔ تماس بازیابی‌کننده تنها ۴ رقم نمایش داده می‌شود، کلیدهای متادیتا که بوی اعتبارنامه می‌دهند (`otp`, `token`, `secret`, `api_key`, …) حذف می‌شوند و تعدادشان با فیلد `redacted` اعلام می‌شود، و خودِ مشاهده هم با عملیات `ADMIN_AUDIT_READ` در همین گزارش ثبت می‌شود. سقف هر صفحه ۱۰۰ ردیف و سقف جابه‌جایی در گزارش ۵۰۰۰ ردیف است تا صفحه‌گردی عمیق، کل لاگ را اسکن نکند.

### امتیاز، بازخورد و گزارش پشتیبانی

اسکیمای `013_feedback_support.sql` دو جدول `order_feedback` و `support_tickets` (با `support_messages` و `support_ticket_events`) را می‌سازد.

**بازخورد سفارش.** امتیاز فقط پس از `DELIVERED` و فقط توسط مشتریِ همان سفارش نوشته می‌شود؛ برای هر سفارش یک ردیف وجود دارد و نویسنده می‌تواند آن را ویرایش کند (پس نیازی به ثبت گزارش جدید برای یک غلط تایپی نیست). امتیاز کسب‌وکار از ۱ تا ۵ لازم است و امتیاز پیک اختیاری است و فقط وقتی پذیرفته می‌شود که سفارش رانندهٔ تخصیص‌یافته داشته باشد. در ثبت اول، صاحب کسب‌وکار اعلان `ORDER_FEEDBACK` (برای امتیاز ۱ یا ۲ با برچسب «نیازمند توجه») و راننده `DRIVER_FEEDBACK` می‌گیرد؛ ویرایش دوباره اعلان نمی‌فرستد، تا یک اصلاح ساده به اسپم تبدیل نشود.
- `GET/PUT /api/v1/orders/:orderId/feedback` برای مشتری همان سفارش (PUT بدنهٔ `{businessRating, driverRating?, comment?}`).
- `GET /api/v1/feedback/businesses/:businessId?limit=&offset=` برای صاحب کسب‌وکار: میانگین امتیازها، تعداد بازخوردها، تعداد موارد نیازمند توجه و آخرین نظرها. `GET /api/v1/feedback/drivers/me` فقط امتیازهای مربوط به خودِ رانندگی کاربر را برمی‌گرداند.
- کادر عملیات: `GET /api/v1/feedback/admin?maxStars=&businessId=` و `DELETE /api/v1/feedback/admin/:id` با بدنهٔ `{reason}`. حذف بدون دلیل پذیرفته نمی‌شود و خودِ حذف با action `FEEDBACK_REMOVED` در جدول ممیزی ثبت می‌شود؛ حذف شده از میانگین هم بیرون می‌رود.
- ستون‌های `feedbackCount`، `feedbackInPeriod`، `averageBusinessRating` و `lowRatingCount` در `GET /api/v1/admin/reports/businesses` از همین جدول با زیرکوئری همبسته خوانده می‌شوند (نه JOIN، تا جمع‌های ریال تکثیر نشوند).

**گزارش پشتیبانی.** تیکت یک گفت‌وگو است، نه یک فرم: گزارش‌دهنده و کادر پیام می‌نویسند و وضعیت با `OPEN → IN_REVIEW → RESOLVED → CLOSED` حرکت می‌کند (از `RESOLVED` می‌توان به `IN_REVIEW` برگشت، از `CLOSED` بیرون آمدن ممکن نیست). `RESOLVED` فقط با یادداشت «چه انجام شد» ثبت می‌شود. پاسخ مشتری روی گزارش `RESOLVED` آن را خودکار به `OPEN` برمی‌گرداند و اولین پاسخ کادر روی گزارش `OPEN` آن را به `IN_REVIEW` می‌برد — هر دو تغییر وضعیت، از جمله نوعِ خودکار، در `audit_logs` با action `SUPPORT_TICKET_STATUS` می‌نشیند. برای یک سفارش، هر نفر فقط یک گفت‌وگوی باز می‌تواند داشته باشد (unique index جزئی) و بستن، جای ثبت گزارش تازه را باز می‌کند. حریفِ سفارش (صاحب کسب‌وکار یا راننده) اعلان می‌گیرد و می‌تواند پاسخ دهد، ولی وضعیت را تغییر نمی‌دهد.
- `POST /api/v1/support/tickets` با `{message, orderId?}`، `GET /api/v1/support/tickets/mine?status=`، `GET /api/v1/support/tickets/:id`، `POST /api/v1/support/tickets/:id/messages` و `PATCH /api/v1/support/tickets/:id/status` با `{status, note?}`.
- صف کادر: `GET /api/v1/support/tickets/admin/queue?status=&search=` که شمارش هر چهار وضعیت را هم برمی‌گرداند و از شمارهٔ تماس گزارش‌دهنده فقط ۴ رقم آخر را می‌دهد؛ جست‌وجو با همان یک عبارت روی نام، شماره و شناسهٔ گزارش کار می‌کند.

در رابط کاربری: دکمهٔ «ثبت امتیاز» در `/orders` برای سفارش‌های تحویل‌شده، بخش «بازخورد مشتریان» در `/business/orders`، «امتیاز تحویل‌ها» در `/driver/deliveries`، و در `/admin/settings` دو بخش «صف پشتیبانی» و «بازخورد سفارش‌ها» کنار گزارش ممیزی. هر سه پنل «گزارش‌های من» را هم دارند و بازکردن اعلانِ یک گزارش، مستقیم داخل همان گفت‌وگو می‌رود (`?ticketId=`). اعلان‌های پشتیبانی: `SUPPORT_TICKET_OPENED`، `SUPPORT_TICKET_MESSAGE`، `SUPPORT_TICKET_RESOLVED`.

### پشتیبان‌گیری و تمرین بازیابی

پشتیبان‌گیری که روزی بازگردانی نشده باشد، فقط یک فایل است. دو اسکریپت در `api/scripts` این را تضمین می‌کنند:

- `npm run db:backup` (با `DATABASE_URL`): یک dump با فرمت custom و فشرده می‌نویسد، کنار آن `sha256` و یک فایل `.rows` با تعداد ردیف‌های لحظهٔ پشتیبان، و فقط `BACKUP_KEEP` نسخهٔ تازه (پیش‌فرض ۱۴) نگه داشته می‌شود. محل پیش‌فرض `backups/` است و در `.gitignore` ثبت شده تا فایل پشتیبان هرگز وارد مخزن نشود. اگر اسکیمای مبدأ جدولی نداشته باشد (مهاجرت‌ها اجرا نشده‌اند) پشتیبان نوشته نمی‌شود و اسکریپت با خطا خارج می‌شود، تا یک فایل خالی به‌جاى پشتیبان باقی نماند.
- `npm run db:restore-drill` (با `DRILL_DATABASE_URL` که به دیتابیس `postgres` اشاره می‌کند): تازه‌ترین dump را در یک دیتابیس موقت با پیشوند `jetino_drill_` بازگردانی می‌کند، اول checksum را می‌سنجد، بعد جدول‌به‌جدول تعداد ردیف‌ها را با همان فایل `.rows` مقایسه می‌کند و تعداد جدول‌های بررسی‌شده را اعلام می‌کند (اگر مقایسه‌ای انجام نشود، تمرین موفق حساب نمی‌شود) و وجود `schema_migrations` را بررسی می‌کند؛ خروجی `pg_restore` هم قضاوت می‌شود، پس اگر ابزار client نسخهٔ جدیدتر از سرور از پیشوند خودش شکایت کرد کار ادامه می‌یابد اما هر خطای دیگری همان‌جا متوقف می‌کند. در حالت شکست با کد ۱ خارج می‌شود و دیتابیس موقت برای بررسی باقی می‌ماند (`KEEP_DRILL_DB=1`)، در حالت موفق آن را حذف می‌کند.

این تمرین در CI به‌عنوان job مستقل `backup-drill` روی هر push اجرا می‌شود (اول build و تست‌ها، بعد seed دمو، پشتیبان، بازگردانی و مقایسه). برای زمان‌بندی روی سرور، یک systemd timer یا cron کافی است:

```
# هر شب ۰۳:۱۰ — پوشهٔ پشتیبان روی همان ماشین، وFileSync به جای دیگر با ابزار خودتان
10 3 * * * cd /srv/jetino/api && BACKUP_DIR=/var/backups/jetino /usr/bin/npm run db:backup >> /var/log/jetino-backup.log 2>&1
```

برای بازیابی واقعی: `createdb jetino_restored`, `pg_restore --no-owner -d jetino_restored <dump>`, و سپس اجرای همان مقایسه با `DRILL_DATABASE_URL`.

### مبدأ فروشگاه و برآورد مسیر

محل هر کسب‌وکار جدا از نشانی مشتری نگهداری می‌شود و مبدأ مسیر پیک است. صاحب کسب‌وکار از پنل خود می‌تواند این نقطه را با نقشهٔ نشان، موقعیت فعلی مرورگر یا ورود دستی مختصات ثبت کند: `PATCH /api/v1/businesses/mine/:id/location` با بدنهٔ `{"latitude":27.2,"longitude":55.7}`. برای پاک کردن محل، هر دو فیلد را خالی بفرستید. نیمه‌ٔ مختصات (فقط عرض یا فقط طول) و مقدار خارج از بازهٔ جغرافیایی رد می‌شود و هر تغییر با action `BUSINESS_LOCATION_UPDATED` در audit log ثبت می‌شود. تا وقتی محل فروشگاه ثبت نشده، هیچ فاصله‌ای ساخته نمی‌شود.

`GET /api/v1/delivery/orders/:orderId/estimate` فاصله و زمان تقریبی بین پین فروشگاه و مختصات تحویلِ همان سفارش را برمی‌گرداند و فقط برای مشتری سفارش، صاحب کسب‌وکار، رانندهٔ تخصیص‌یافته و کادر عملیات باز است. پاسخ موفق: `{available:true, source:"NESHAN"|"ESTIMATED", distanceMeters, durationMinutes, cached, measuredAt, note?}`. مسیر واقعی از سرویس مسیریابی نشان (`https://api.neshan.org/v4/direction?type=car&origin=lat,lng&destination=lat,lng`) با هدر `Api-Key` خوانده می‌شود؛ کلید هرگز در URL، لاگ یا پاسخ نمی‌آید و خطای نشان (تایم‌اوت، سهمیه، پاسخ نامعتبر) وضعیت سرویس را نمی‌شکند: در آن حالت مقدار `ESTIMATED` از خط مستقیم با ضریب مسیر ۱٫۳۵ و سرعت میانگین ۴۳۰ متر بر دقیقه محاسبه و برچسب‌گذاری می‌شود. نتیجهٔ مسیرهای نشان برای ۱۵ دقیقه در حافظهٔ همان پروسه کش می‌شود (حداکثر ۵۰۰ کلید، با تعویض قدیمی‌ترین)؛ کلید کش شامل خود مختصات است، پس جابه‌جا یا پاک کردن پین فوراً برآورد را بی‌اعتبار می‌کند. برای محیط‌های چندنسخه‌ای Redis جایگزین این کش درون‌فرآیندی است.

متغیرهای سرور: `NESHAN_SERVER_KEY` (بدون آن فقط برآورد تقریبی داده می‌شود)، `NESHAN_DIRECTION_URL`، `NESHAN_DIRECTION_TYPE` با مقادیر `car|walk|transit|bicycle`، و `NESHAN_TIMEOUT_MS` (بین ۵۰۰ تا ۱۵۰۰۰ میلی‌ثانیه). پنل راننده برآورد سفارش‌های فعال را همراه با دکمهٔ «شروع مسیر» نشان می‌دهد و منبع عدد (نشان یا تقریب) را از کاربر پنهان نمی‌کند.

### نشانی، پیش‌فاکتور و سفارش نقدی

فرم نشانی امکان افزودن مختصات موقعیت فعلی با اجازهٔ مرورگر یا ویرایش دستی طول و عرض جغرافیایی را دارد؛ مختصات اختیاری‌اند و نشانی متنی همچنان لازم است. مختصات هنگام ثبت سفارش snapshot می‌شود و در پنل راننده با پیوند `geo:` برای بازکردن در نقشهٔ دستگاه نمایش داده می‌شود. نقشهٔ تعاملی نشان برای انتخاب/اصلاح نشانگر افزوده شده است. کلید عمومی مرورگر را در `VITE_NESHAN_API_KEY` تنظیم و در داشبورد نشان به originهای مجاز محدود کنید؛ کلید در باندل مرورگر قرار می‌گیرد و نباید کلید محرمانهٔ سرور باشد.

- `GET/POST /api/v1/addresses` و `PATCH/DELETE /api/v1/addresses/:id` برای نشانی‌های متعلق به کاربر واردشده.
- `POST /api/v1/orders/quote` قیمت جاری محصولات، کرایه و کمیسیون را سمت سرور محاسبه می‌کند؛ پیش‌فاکتور رزرو نیست.
- `POST /api/v1/orders` سفارش نقدی ثبت می‌کند. هدر `Idempotency-Key` الزامی است؛ مبلغ ارسالی از کلاینت پذیرفته نمی‌شود و سرور قیمت‌ها را در تراکنش دوباره محاسبه می‌کند.
- `GET /api/v1/orders/mine`, `GET /api/v1/orders/:id`, `POST /api/v1/orders/:id/cancel` برای سفارش‌های مشتری؛ `GET /api/v1/orders/business/mine` و `PATCH /api/v1/orders/:id/status` برای کسب‌وکار مالک.
- `GET /api/v1/notifications`, `PATCH /api/v1/notifications/:id/read` و `POST /api/v1/notifications/read-all` برای اعلان‌های درون‌برنامه‌ای همان کاربر.
- کسب‌وکار هنگام تأیید سفارش می‌تواند زمان آماده‌سازی تقریبی (۵ تا ۲۴۰ دقیقه، پیش‌فرض ۳۰ دقیقه) را اعلام کند؛ این زمان در سفارش ذخیره و به مشتری در اعلان و جزئیات پیگیری نمایش داده می‌شود.
- پیش از تأیید کسب‌وکار، مشتری می‌تواند سفارش را لغو کند. برای مسیر کسب‌وکار وضعیت‌های تأیید/رد، آماده‌سازی و آمادهٔ تحویل به پیک پشتیبانی می‌شود.
- مدیر کل از بخش «ارسال و رانندگان» در `/admin/settings` رانندهٔ فعال را به سفارش آماده تخصیص می‌دهد. کاربر راننده باید ابتدا با OTP وارد شده باشد؛ مدیر کل حساب او را به راننده تبدیل می‌کند.
- مسیر `/driver/deliveries` برای حرکت به «در مسیر» و «تحویل‌شده» است؛ پس از تحویل، راننده دریافت کامل وجه نقد را صریحاً تأیید می‌کند و پرداخت از `PENDING` به `PAID` می‌رود. رویداد وصول در `cash_collections` و audit ثبت می‌شود.
- رابط مشتری از دیتابیس فهرست/منو می‌گیرد؛ مسیر `/orders` پیگیری مشتری، `/notifications` اعلان‌های درون‌برنامه‌ای، `/business/orders` پنل سفارش‌های کسب‌وکار و `/business/menu` مدیریت دسته‌بندی و موجودی محصولات است. مدیریت منو از APIهای `GET /api/v1/businesses/mine/:id/menu`, `PATCH /api/v1/businesses/mine/:id/orderability`, `POST /api/v1/businesses/:id/categories`, `POST /api/v1/businesses/categories/:categoryId/products`, `PATCH /api/v1/businesses/products/:productId` و `PATCH /api/v1/businesses/products/:productId/availability` استفاده می‌کند و همه به مالک کسب‌وکار محدودند. Push و SMS عملیاتی (غیر از OTP) و پرداخت آنلاین هنوز متصل نیستند.

### تصویر غذا و شناسایی پیک در تحویل

هنگام افزودن یا ویرایش محصول، صاحب کسب‌وکار عکس واقعی غذا را انتخاب می‌کند (`PhotoField`). مرورگر عکس را پیش از ارسال تا حداکثر ۱۲۰۰ پیکسل کوچک و به JPEG فشرده می‌کند و API فقط `https` یا data URL معتبر با امضای واقعی فایل (JPEG/PNG/WebP) تا ۳۰۰ کیلوبایت را می‌پذیرد؛ SVG و آدرس‌های غیرامن رد می‌شوند (`api/src/security/security.util.ts`). تصویر در `products.image_url` ذخیره و در `GET /api/v1/businesses/:id` و `GET /api/v1/businesses/mine/:id/menu` برگردانده می‌شود؛ فروشگاه عکس واقعی را نشان می‌دهد و فقط وقتی عکسی نیست به تصویر پیشنهادی دسته‌بندی برمی‌گردد.

راننده پیش از دریافت مأموریت باید «نام و نام خانوادگی، نوع وسیله، شمارهٔ پلاک و عکس خود» را در `PATCH /api/v1/drivers/me` ثبت کند (`GET /api/v1/drivers/me` وضعیت و فیلدهای ناقص را می‌دهد). پلاک به فرمت ایران نرمال می‌شود (`۱۲ ب ۳۴۵۶۷` → `12ب34567`) و ایندکس یکتا نمی‌گذارد دو حساب یک پلاک داشته باشند. تخصیص سفارش در `api/src/admin/admin-orders.service.ts` تا کامل‌شدن این چهار قلم رد می‌شود، و هویت پیک به مشتری (`GET /api/v1/orders/:id` و `GET /api/v1/orders/mine`) و کسب‌وکار (`GET /api/v1/orders/business/mine`) با نام، پلاک، نوع وسیله و عکس برمی‌گردد؛ کنترل عملیات هم همین را در فهرست سفارش‌ها می‌بیند.

کد تحویل: هر سفارش یک کد چهاررقمی می‌گیرد. فقط هش کد مقایسه می‌شود (`delivery_code_hash`)، نسخهٔ رمزشده با AES-GCM در `delivery_code_encrypted` نگه داشته می‌شود تا مشتری آن را در صفحهٔ پیگیری ببیند، و راننده برای `PATCH .../status` با `{"status":"DELIVERED","code":"4321"}` باید همان کد را وارد کند. هر تلاش ناموفق در `delivery_code_attempts` ثبت می‌شود، پس از ۵ تلاش کد قفل می‌شود و به مشتری اعلان `DELIVERY_CODE_LOCKED` می‌رسد؛ همهٔ این‌ها در `audit_logs` (`DELIVERY_CODE_REJECTED`) ثبت می‌شوند. سفارش‌های قدیمی که کد ندارند مثل قبل تحویل می‌شوند.

درخواست رانندگی (`POST /api/v1/partner-applications/drivers`) هم پلاک و عکس را الزامی می‌کند و تأیید مدیر همان هویت را روی `drivers` می‌نویسد، پس رانندهٔ تأییدشده بلافاصله قابل تخصیص است. مهاجرت‌های `018_media_and_driver_identity.sql` و `019_application_identity.sql` این ستون‌ها را اضافه می‌کنند و نام نمایشی کاربر و آخرین درخواست تأییدشده را برای راننده‌های موجود پر می‌کنند.

### موقعیت زنده، تأیید مدارک پیک و دکمهٔ اضطراری

- **موقعیت زنده:** راننده در پنل خود دکمهٔ «اشتراک موقعیت» را روشن می‌کند؛ مرورگر با `watchPosition` حداکثر هر ۸ ثانیه یک نقطه به `POST /api/v1/drivers/me/location` می‌فرستد. این مسیر فقط وقتی مأموریت `DRIVER_ASSIGNED`/`OUT_FOR_DELIVERY` دارد پذیرفته می‌شود، در `driver_locations` (یک ردیف به‌ازای هر پیک) upsert می‌شود و با `DELETE` یا پایان تحویل پاک می‌شود. `GET /api/v1/delivery/orders/:orderId/tracking` برای مشتری، کسب‌وکار، خود پیک و کارکنان موقعیت را با فاصله/زمان تقریبی، هویت پیک و وضعیت تأیید برمی‌گرداند؛ نقطهٔ قدیمی‌تر از ۲ دقیقه هرگز به‌عنوان «زنده» نمایش داده نمی‌شود و با `stale: true` و ساعت آخرین مشاهده می‌آید.
- **تأیید مدارک:** پیک کارت ملی و یک سلفی تازه را با `POST /api/v1/drivers/me/verification` می‌فرستد (چرخهٔ `UNVERIFIED → PENDING → APPROVED/REJECTED`، تاریخچه در `driver_verification_history`). کارشناس در `GET /api/v1/admin/drivers/verification?status=PENDING` صف را می‌بیند و با `PATCH /api/v1/admin/drivers/verification/:id` تصمیم می‌گیرد؛ تأیید بدون تیک صریح `selfieMatch: true` رد می‌شود تا سامانه هیچ‌وقت ادعای تطبیق خودکار نکند. تنظیم `require_driver_verification` (پیش‌فرض ۰) با `PATCH /api/v1/admin/settings` و کلید `requireDriverVerification` روشن/خاموش می‌شود؛ وقتی روشن باشد تخصیص مأموریت به پیک تأییدنشده با پیام فارسی رد می‌شود.
- **دکمهٔ اضطراری:** هر طرف سفارش با `POST /api/v1/safety/sos` (`orderId` + `category` از `UNSAFE|HARASSMENT|ACCIDENT|OTHER` + یادداشت اختیاری تا ۵۰۰ نویسه) گزارش می‌سازد. ایندکس یکتای «یک گزارش باز برای هر نفر/سفارش» از پرکردن صف با فشار دوباره جلوگیری می‌کند. کارکنان صف را با `GET /api/v1/admin/safety/events?status=OPEN` می‌بینند و با `PATCH /api/v1/admin/safety/events/:id` («برداشتن» یا «بستن با نتیجهٔ مکتوب») پاسخ می‌دهند؛ هر تغییر اعلان و audit دارد.
- **محدودیت نرخ:** `RateLimitService` شمارنده را در جدول `rate_limit_counters` و روی پنجرهٔ ثابت نگه می‌دارد تا همهٔ نمونه‌های سرورلس همان سقف را ببینند: ثبت سفارش ۳۰/۱۰ دقیقه، درخواست کد ۶/۱۵ دقیقه، تلاش تأیید کد ۱۲/۱۵ دقیقه، گزارش ایمنی ۵/۱۰ دقیقه و ارسال موقعیت ۱۲۰/دقیقه. اگر جدول شمارنده در دسترس نباشد درخواست رد نمی‌شود (fail-open) چون این سقف‌ها ترمز سوءاستفاده‌اند نه کنترل دسترسی؛ خود مجوزها جای دیگری بررسی می‌شوند.
- **احراز هویت رسمی پیک (زحل):** جدا از تأیید دستی مدارک، پیک کد ملی/تاریخ تولد/سریال کارت ملی را با `POST /api/v1/drivers/me/identity/verify` می‌فرستد؛ سرور اول شاهکار (موبایل همان کد ملی است؟) و بعد ثبت احوال را می‌گیرد. مرحلهٔ دوم یک ویدئوی سلفی تازه است (`POST /api/v1/drivers/me/identity/biometric` با فایل خام webm/mp4 تا ۴ مگابایت) که به جلسهٔ Liveness زحل می‌رود و نتیجه‌اش با `GET` همان مسیر خوانده می‌شود. هر فراخوانی در `identity_checks` ثبت می‌شود، «عدم تطبیق» به‌عنوان خطا دروغ گفته نمی‌شود، و تنظیم `require_driver_identity` (پیش‌فرض ۰) مأموریت دادن به پیک احرازنشده را می‌بندد. راهنمای کامل: [`docs/IDENTITY.md`](docs/IDENTITY.md).
- کلیدهای بیرونی: موقعیت از GPS مرورگر، مدارک به‌صورت عکس فشرده در همان دیتابیس، و هشدار در صف داخلی می‌نشیند؛ برای احراز هویت رسمی فقط `ZOHAL_TOKEN`/`ZOHAL_BIOMETRIC_TOKEN` لازم است. راهنمای کامل همهٔ کلیدها و سرویس‌های ابری (کاوه‌نگار، نشان، زحل، VAPID، Supabase، Vercel و اختیاری‌ها) در [`docs/EXTERNAL-SERVICES.md`](docs/EXTERNAL-SERVICES.md) است.
- مهاجرت `020_tracking_verification_safety.sql` این جدول‌ها و ستون‌ها را می‌سازد؛ روی محیط فعلی اعمال و در `schema_migrations` ثبت شده است.
- **جست‌وجوی زنده:** هر تایپ در کادر هیرو با ۲۲۰ میلی‌ثانیه تأخیر و لغو درخواست قبلی به `GET /api/v1/businesses?q=` می‌رود و تا ۶ نتیجه را زیر کادر نشان می‌دهد.
- **چیدمان واکنش‌گرا:** هدر ۷۲/۶۲، هدف لمسی ۴۴px، منوی متنی تا ۱۲۴۰ و بعد تب‌بار ۵ آیتمی پایین؛ «پیشنهاد امروز» در لپ‌تاپ کارت و در تبلت/موبایل ردیف می‌شود. جدول نقطه‌های شکست و اندازه‌های استاندارد در [`docs/APPEARANCE.md`](docs/APPEARANCE.md#۹-چیدمان-واکنشگرا-استانداردها-و-نقطههای-شکست) آمده و ۱۲ عرض ۳۲۰ تا ۱۹۲۰ اندازه‌گیری شده است.
- **صفحهٔ اصلی تصویرمحور:** هیروی عکاسی‌شده (`hero-feast.jpg`)، ردیف «پیشنهاد امروز» با سه کسب‌وکار اول، و سه بنر تصویری (سوپرمارکت، غذای محلی، کافه و دسر)؛ عکس همهٔ کارت‌ها از `public/images` و با `photoFor()` انتخاب می‌شود. فرم لیست خرید روی صفحهٔ اصلی نیست و بنر سوپرمارکت با دکمهٔ «ورود به سوپرمارکت» به `/grocery` می‌رود.
- **ظاهر، حرکت و لودینگ:** لایهٔ آخر CSS (`src/liquid.css`) و `src/ui/motion.tsx` نور مایع پس‌زمینه، نوار پیشرفت مایع (روی هر `fetch`)، لودر قطره‌ای و اسکلت‌های شیمری همهٔ صفحه‌ها را می‌سازند؛ صفحهٔ بوت داخل `index.html` است تا پیش از باندل هم برند دیده شود. با `prefers-reduced-motion` همهٔ این حرکت‌ها خاموش می‌شود. جزئیات و فهرست مصرف‌کننده‌ها: [`docs/APPEARANCE.md`](docs/APPEARANCE.md#۷-لایهٔ-مایع-و-صفحات-لودینگ).

### دفتر ارسال اعلان‌ها و زمان‌بند

هر اعلانی که سرور می‌نویسد، در همان تراکنش یک ردیف `IN_APP` و به‌ازای هر دستگاه فعال یک ردیف `PUSH` در `notification_deliveries` می‌گیرد (تریگر `trg_notifications_queue_delivery`)؛ هیچ مسیر جدیدی نمی‌تواند اعلانی بدون ردیف ارسال بسازد. `notify(..., {dedupeKey})` کلید تکرار را در دیتابیس قفل می‌کند (ایندکس یکتای جزئی) و در نتیجهٔ دوباره‌کوشی سفارش یا تیکت، اعلان تکراری ساخته و ارسال نمی‌شود. کاربر هدف می‌تواند رویدادها را خاموش کند (`GET/PUT /api/v1/notifications/push/preferences`) و ردیف `SKIPPED` با دلیل روی همان اعلان در inbox دیده می‌شود.

مسیرهای مدیر کل: `GET /api/v1/notifications/delivery/stats`، `GET /api/v1/notifications/delivery/queue?state=`، `POST /api/v1/notifications/delivery/:id/retry`، `POST /api/v1/notifications/dispatch` و `GET /api/v1/notifications/dispatch` (ویژهٔ زمان‌بند، با هدر `Authorization: Bearer $CRON_SECRET`). پنل مدیر کل در `/admin` همین دفتر را با فیلتر وضعیت و دکمهٔ «اجرای صف» نشان می‌دهد. تحویل at-least-once است: هر ردیف تا ۵ تلاش با فاصلهٔ ۳۰/۱۲۰/۶۰۰/۱۸۰۰ ثانیه، و اشتراکی که سرویس ارسال آن را رد کند (۴۰۴/۴۱۰) غیرفعال می‌شود.

برای فعال‌شدن واقعی وب‌پوش، `VAPID_PUBLIC_KEY`، `VAPID_PRIVATE_KEY` و `VAPID_SUBJECT` را تنظیم کنید (`npx web-push generate-vapid-keys`). بدون آن‌ها صف باز می‌ماند و اعلان‌ها `SKIPPED` با دلیل `PUSH_NOT_CONFIGURED` می‌شوند — نه `SENT` صوری.

### حساب‌های آزمایشی هر پنل

ورود جتینو فقط با کد یک‌بارمصرف پیامکی است و راه میانبار یا کد ثابت ندارد. برای اینکه محیطی که کلید کاوه‌نگار ندارد هم بتواند از سر تا سر تست شود، `npm run db:seed:accounts` (در `api`) شش شمارهٔ ثابت با نقش‌های لازم می‌سازد: مشتری، صاحب کسب‌وکار، راننده، مدیر عملیات، مدیر ارشد و پشتیبان — به‌همراه یک کسب‌وکار فعال با دو محصول و یک نشانی پیش‌فرض، تا پنل‌ها دادهٔ واقعی برای نشان‌دادن داشته باشند.

| `09120000025` | SUPER_ADMIN | `/admin` تنظیمات مالی، تأیید کسب‌وکارها، audit log |
| `09120000026` | SUPPORT | `/operations` و `/notifications` پاسخ به تیکت و بازبینی امتیازها |

این ردیف‌ها هیچ رمزی ندارند و تنها با کد OTP قابل ورودند. اگر `JETINO_ALLOW_TEST_OTP=yes` روی سرور تنظیم شده باشد و کلید پیامک تنظیم نباشد، `POST /api/v1/auth/otp/request` کد را در بدنهٔ پاسخ برمی‌گرداند (`testCode`) و هر کادر ورود همان کد را به‌جای «کد پیامک می‌شود» نشان می‌دهد، پس نیازی به دیدن شبکهٔ مرورگر نیست؛ همان کد در دیتابیس فقط به‌صورت digest ذخیره می‌شود، مهلت پنج‌دقیقه، سقف پنج تلاش و مصرف‌شدن یک‌باره سر جای خود است. با حذف آن متغیر، در بسته می‌شود و پاسخ دوباره ۵۰۳ می‌دهد. این پرچم را در محیط واقعی روشن نگذارید؛ روی محیط ابریِ تستِ همین مخزن روشن است و باید پیش از محیط واقعی حذف شود.

### استقرار روی Vercel و Supabase

`vercel.json` دو خروجی می‌سازد: سایت ایستا از `dist` و یک تابع `api-server.cjs` (در ریشهٔ مخزن، چون بیلدرِ Vercel پوشهٔ فایل ورودی را ریشهٔ تابع می‌گیرد و از `server/` نمی‌شود به `api/` رسید) که همان `AppModule` نتس‌جی را درون خود بالا می‌آورد و `/api/*` به آن می‌رود؛ تشخیص خودکار framework خاموش است تا فایل‌های زیر `api/` به‌جای یک تابع، ده‌ها تابع نشوند. `scripts/vercel-build.cjs` هنگام build، وابستگی‌های `api` را نصب، بیلد و مایگریشن را اجرا می‌کند.

متغیرهای لازم در پروژه (نه در مخزن): `DATABASE_URL` (استخر `aws-0-eu-central-1.pooler.supabase.com:5432` با `?sslmode=require`)، `JWT_SECRET`، `OTP_HMAC_SECRET`، `CRON_SECRET` و در صورت نیاز کلیدهای VAPID. برای استخر سوپابیس `DATABASE_URL` را با `?sslmode=no-verify` بگذارید (گواهی استخر زنجیرهٔ self‑signed دارد و حالت `require` در `pg` همان `verify-full` است)؛ برای اتصال مستقیم می‌توانید `?sslmode=verify-full&sslrootcert=/path/supabase-ca.pem` بدهید. `DATABASE_URL_TEST` تنها در CI پر می‌شود.

اگر اسکیما را برون از این مخزن ساخته‌اید (مثلاً با `supabase db push` یا بازگردانی یک backup)، جدول `schema_migrations` خالی است و `db:migrate` اولین مایگریشن را دوباره اجرا می‌کند و روی همان قیدِ از‌قبل‌موجود می‌شکند. یک‌بار `npm run db:baseline` را در `api` اجرا کنید: نام فایل‌های اعمال‌شده را در دفتر ثبت می‌کند و هیچ شیءای در دیتابیس نمی‌سازد. پیش‌فرض آن dry run است و با کد خروجی ناموفق می‌ایستد؛ نوشتن فقط با `BASELINE_CONFIRM=yes` انجام می‌شود، چون این فرمان ادعا می‌کند SQL از قبل اجرا شده است.

دو زمان‌بند وجود دارد و هر دو یک کار را می‌کنند، پس نبود یکی خطرناک نیست: `crons` در `vercel.json` روزی یک‌بار (سقف طرح رایگان Vercel) و `.github/workflows/notification-sweep.yml` هر پنج دقیقه. برای فعال‌کردن دومی در مخزن به `Settings → Secrets and variables → Actions` بروید: در تب Variables یک `JETINO_API_URL` با آدرس محیط (مثلاً `https://jetino-omega.vercel.app`) و در تب Secrets یک `JETINO_CRON_SECRET` با همان مقدار `CRON_SECRET` پروژهٔ Vercel بسازید. وارد هیچ حسابی نمی‌شود: زمان‌بند همان هدر `Authorization: Bearer` را به `GET /api/v1/notifications/dispatch?limit=50` می‌فرستد (نسخهٔ `POST` این مسیر مخصوص دکمهٔ «اجرای صف» در پنل ادمین است و به سشن کارمندی نیاز دارد) و `tests` این تطابق را قفل می‌کند. تمرین بازیابی هفتگی (§۷٫۳) هم با `schedule` در `ci.yml` اجرا می‌شود؛ زمان‌بند گیت‌هاب فقط از شاخهٔ پیش‌فرض اجرا می‌شود، پس تا این فایل‌ها در `main` نرفته‌اند، صف با همان کوشش روزانهٔ Vercel پیش می‌رود.

### استقرار روی چابکان (یک سرویس Docker)

`Dockerfile` ریشه، فرانت و API را در یک تصویر می‌سازد و `scripts/docker-entrypoint.sh` پیش از بالا آمدن سرور مایگریشن‌ها را اعمال می‌کند؛ بعد یک پروسهٔ Node هم `/api/v1/*` را جواب می‌دهد و هم صفحه‌های ساخته‌شدهٔ Vite را (با فالبک SPA برای `/admin`, `/driver`, `/grocery`). یک origin یعنی نه CORS لازم است و نه آدرس مطلق API در زمان build. اتصال دیتابیس می‌تواند `DATABASE_URL` باشد یا شکل جدا شدهٔ پنل (`DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_PORT`, `DB_SSL`) که `api/src/config/database-url.ts` جمع می‌کند؛ `PORT` عمداً برای دیتابیس خوانده نمی‌شود چون همان پورت HTTP است. راهنمای گام‌به‌گام (ساخت دیتابیس، سرویس، ثبت پورت ۳۰۰۰، متغیرها، اولین مدیر، دامنه، زمان‌بند، بکاپ و عیب‌یابی): [`docs/DEPLOY-CHABOKAN.md`](docs/DEPLOY-CHABOKAN.md). بدون `STATIC_DIR` رفتار قبلی (Vite در توسعه، Vercel در تولید) دست‌نخورده می‌ماند.

> دادهٔ نمایشی فقط با `npm run db:seed:demo` و فقط در محیط توسعه ساخته می‌شود. کد OTP آزمایشی یا میان‌بر ورود وجود ندارد.
