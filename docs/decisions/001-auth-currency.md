# تصمیم‌های جتینو — مرحلهٔ ۳

## DEC-001 — واحد پول
- وضعیت: قطعی
- انتخاب: ریال
- دلیل: انتخاب صریح مالک محصول.
- پیامد فنی: مبلغ‌ها در دیتابیس به‌صورت عدد صحیحِ ریال (`*_rial`) ذخیره می‌شوند؛ تبدیل ممیزشناور استفاده نمی‌شود.
- تاریخ: ۲۰۲۶-۱۱-۱۷

## DEC-002 — ارائه‌دهندهٔ OTP
- وضعیت: انتخاب محصول، اتصال نیازمند پیکربندی/اعتبارسنجی
- انتخاب: کاوه‌نگار
- پیامد فنی: اتصال verify/lookup پشت تنظیمات محیطی، با کد منقضی‌شونده و محدودیت تعداد درخواست/تلاش.
- نکته: ارسال واقعی تا زمان پیکربندی کلید API و قالب تأیید در محیط، فعال/قابل‌آزمایش نیست.
- تاریخ: ۲۰۲۶-۱۱-۱۷

## DEC-003 — بک‌اند
- وضعیت: قطعی برای شروع پیاده‌سازی
- انتخاب: NestJS + PostgreSQL در قالب Modular Monolith.
- پیامد فنی: API نسخه‌دار REST و migrationهای SQL نسخه‌بندی‌شده.
- تاریخ: ۲۰۲۶-۱۱-۱۷

## DEC-004 — روش محاسبهٔ ارسال
- وضعیت: قطعی برای مدل داده؛ مبلغ باز
- انتخاب: کرایهٔ ثابت به‌ازای هر منطقه.
- پیامد فنی: مبلغ قابل‌تنظیم در تنظیمات منطقه و snapshot ریالی در سفارش؛ تا زمان تعیین مبلغ منطقه، ثبت سفارش باید متوقف بماند.
- تاریخ: ۲۰۲۶-۱۱-۱۷

## DEC-005 — مقدارهای آغازین مالی
- وضعیت: موقت، قابل ویرایش توسط SUPER_ADMIN
- کرایهٔ ثابت آغازین بندر خمیر: ۵۰۰٬۰۰۰ ریال برای هر سفارش.
- کمیسیون پیش‌فرض آغازین پلتفرم: ۱٬۰۰۰ نقطهٔ پایه (۱۰٪)؛ کسب‌وکار می‌تواند نرخ مستقل داشته باشد.
- دلیل: مالک محصول خواست فعلاً مقدار پیش‌فرض فعال باشد و بعداً از پنل مدیر کل قابل تغییر بماند؛ این دو مقدار صرفاً نقطهٔ شروع عملیاتی‌اند، نه نرخ نهایی تأییدشدهٔ تجاری.
- پیامد فنی: مقدار ارسال در رکورد منطقه و کمیسیون پیش‌فرض در تنظیمات پلتفرم نگهداری می‌شود؛ endpoint مدیریتی فقط برای SUPER_ADMIN قابل دسترسی است؛ هر تغییر audit می‌شود. نرخ و هزینه هنگام ثبت سفارش باید snapshot شوند.
- تاریخ: ۲۰۲۶-۱۱-۱۷

## DEC-006 — روش پرداخت و فعال‌سازی ثبت سفارش
- وضعیت: باز؛ فعال‌سازی خرید به تعویق افتاد
- انتخاب فعلی: تا انتخاب روش پرداخت/درگاه، ثبت سفارش واقعی فعال نشود؛ زیرساخت توسعه ادامه پیدا کند.
- پیامد فنی: فرانت‌اند و بک‌اند نباید سفارش موفق یا پرداخت نمایشی ثبت کنند.
- تاریخ: ۲۰۲۶-۱۱-۱۷
