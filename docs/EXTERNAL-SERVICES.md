# سرویس‌های بیرونی جتینو: هر کلید از کجا، کجا ثبت شود

این فایل فهرست کامل کلیدها و سرویس‌های بیرونی است: چه چیزی همین حالا برای اجرای واقعی لازم است، هر کلید از کدام صفحه گرفته می‌شود، در کدام متغیر می‌نشیند، و از کجا بفهمیم درست کار می‌کند.

دو محل ثبت وجود دارد و هر دو باید هم‌خوان بمانند:

1. **محلی** — فایل `.env` در ریشهٔ مخزن (از `.env.example` کپی کنید). API آن را با `dotenv` می‌خواند؛ Vite فقط متغیرهای با پیشوند `VITE_` را به مرورگر می‌دهد.
2. **Vercel** — `Project → Settings → Environment Variables`. برای هر متغیر محیط‌های Production/Preview/Development را انتخاب کنید و پس از تغییر، **Redeploy** بزنید (متغیرها فقط در build بعدی اثر می‌کنند). متغیرهای `VITE_*` در زمان build داخل بستهٔ فرانت نوشته می‌شوند، پس بدون build دوباره اعمال نمی‌شوند.

> قاعدهٔ طلایی: کلید سروری (Kavenegar، Neshan server، VAPID private، DATABASE_URL، JWT/HMAC) هرگز نباید `VITE_` بگیرد. هر چیزی که در مرورگر لازم است، مثل کلید نقشه، باید در پنل سرویس به دامنه‌های خودتان محدود شود.

## ۲) Supabase (پایگاه داده) — `DATABASE_URL`

**چه چیزی می‌دهد:** PostgreSQL مدیریت‌شده، پشتیبان روزانه، کنسول SQL.

**گرفتن اتصال:**

1. وارد `supabase.com/dashboard` شوید و پروژهٔ `ahckqhqqgcpplplbavrl` را باز کنید.
2. `Project Settings → Database → Connection string → URI` را بردارید.
3. برای سرورلس دو گزینه دارید:
   - **Pooler / Transaction mode** (پیشنهادی برای Vercel): میزبان `aws-0-eu-central-1.pooler.supabase.com`، پورت `6543`، نام کاربری `postgres.<ref>`.
   - **Session mode**: پورت `5432`.
4. رمز دیتابیس را در همان صفحه از `Reset database password` می‌سازید؛ فقط یک بار نشان داده می‌شود.

**شکل درست متغیر (نمونه):**

```
DATABASE_URL=postgresql://postgres.ahckqhqqgcpplplbavrl:RAMZ@aws-0-eu-central-1.pooler.supabase.com:6543/postgres?sslmode=no-verify
```

`sslmode=no-verify` برای استخر سوپابیس لازم است چون گواهی آن زنجیرهٔ self-signed دارد و `pg` حالت `require` را مثل `verify-full` می‌بندد. برای اتصال مستقیم می‌توانید `?sslmode=verify-full&sslrootcert=/path/supabase-ca.pem` بدهید.

**اجرای مهاجرت‌ها:** `cd api && npm run db:migrate` (با `DATABASE_URL` محلی/ابری). در محیط ابری، `scripts/vercel-build.cjs` همین کار را در build انجام می‌دهد؛ اگر جدولی جا افتاد، SQL فایل `api/src/database/migrations/020_tracking_verification_safety.sql` را در `SQL Editor` اجرا و نامش را در `schema_migrations` ثبت کنید.

**تست:** `curl -s https://<host>/api/v1/health` باید `{"status":"ok","service":"jetino-api"}` بدهد و یک فروشگاه واقعی برگردد: `GET /api/v1/businesses/20000000-0000-4000-8000-000000000031`.

**چرخش کلید:** رمز دیتابیس را در Supabase عوض کنید، `DATABASE_URL` را در Vercel به‌روز و Redeploy کنید. اتصال‌های قدیمی قطع می‌شوند؛ چند ثانیه ۵۰۰ دیدن طبیعی است.

## ۳) Vercel (میزبانی و زمان‌بند) — `CRON_SECRET`

- پروژه: `jetino` (`prj_2qbXHjCHdiq9aIwOD3FKWxjvgAaz`)، دامنهٔ فعلی `jetino-omega.vercel.app`.
- `vercel.json` دو خروجی می‌سازد: سایت ایستا از `dist` و تابع `api-server.cjs` برای `/api/*`.

**`CRON_SECRET` چیست:** یک رشتهٔ تصادفی ≥۳۲ نویسه که فقط زمان‌بند و پنل ادمین آن را می‌دانند؛ مسیر `GET /api/v1/notifications/dispatch` با هدر `Authorization: Bearer $CRON_SECRET` صف اعلان را پیش می‌برد.

تولید:

```bash
openssl rand -hex 32
```

ثبت در محیط: `Vercel → Project → Settings → Environment Variables → CRON_SECRET`، و در `.env` محلی همان مقدار.

**کرون:** در `vercel.json` یک `crons` روزانه (`0 0 * * *`) روی `/api/v1/notifications/dispatch` هست (سقف طرح رایگان). اگر صف باید هر ۵ دقیقه پیش برود، ورک‌فلوی `.github/workflows/notification-sweep.yml` را با دو متغیر مخزن فعال کنید: `JETINO_API_URL` (Variable) و `JETINO_CRON_SECRET` (Secret، همان مقدار).

**تست:**

```bash
curl -s -H "Authorization: Bearer $CRON_SECRET" https://jetino-omega.vercel.app/api/v1/notifications/dispatch?limit=5
```

بدون هدر باید ۴۰۱/۴۰۳ بدهد؛ اگر ۲۰۰ داد، یعنی راز تنظیم نشده و مسیر باز است — همان لحظه متغیر را بگذارید.

## ۴) کاوه‌نگار (پیامک کد ورود) — `KAVENEGAR_API_KEY` + `KAVENEGAR_OTP_TEMPLATE`

**مراحل گرفتن:**

1. در `kavenegar.com` ثبت‌نام و پنل را باز کنید (`panel.kavenegar.com`).
2. خط خدماتی/شمارهٔ فرستنده بگیرید (برای OTP معمولاً خط اختصاصی یا خدماتی لازم است؛ کارت بانکی/احراز هویت کسب‌وکار می‌خواهد).
3. از پنل، **API Key** را از بخش تنظیمات/کلیدهای API بردارید.
4. در بخش **قالب‌ها (Verify templates)** یک قالب بسازید، مثلاً:
   ```
   کد ورود شما به جتینو: %token%
   ```
   نام قالب را دقیقاً همان چیزی بگذارید که در `KAVENEGAR_OTP_TEMPLATE` می‌نویسید (حروف کوچک، بدون فاصله).
5. کلید و نام قالب را در `.env` و Vercel ثبت کنید.

API مورد استفاده در کد:

```
GET https://api.kavenegar.com/v1/{API_KEY}/verify/lookup.json?receptor=98912...&token=123456&template=jetino-otp
```

`status === 200` در پاسخ یعنی پذیرفته شد؛ هر چیز دیگر باعث ۵۰۳ فارسی «ارسال پیامک انجام نشد» می‌شود و ردیف OTP مصرف‌شده علامت می‌خورد.

**بدون پیامک، فقط برای تست:** `JETINO_ALLOW_TEST_OTP=yes` را فقط روی محیط آزمایشی بگذارید؛ آن‌وقت کد در پاسخ `POST /api/v1/auth/otp/request` به‌صورت `testCode` برمی‌گردد و همان کد روی صفحه نشان داده می‌شود. این پرچم را روی محیط واقعی روشن نگذارید.

**هزینه:** pay-as-you-go؛ برای OTP الگوی «verify» معمولاً ارزان‌تر از پیامک انبوه است. محدودیت نرخ سمت ما: ۳ چالش در ۱۵ دقیقه برای هر شماره + سقف دیتابیسی ۶ درخواست/۱۵ دقیقه و ۱۲ تلاش تأیید/۱۵ دقیقه.

## ۵) نشان (نقشه و مسیریابی) — دو کلید جدا

### ۵-۱) `NESHAN_SERVER_KEY` (سرور)

1. `platform.neshan.org` → ساخت حساب → `داشبورد → کلیدهای API` (API Keys).
2. سرویس **Direction / Routing** را فعال کنید (پلن رایگان سهمیهٔ روزانه دارد).
3. کلید را در `NESHAN_SERVER_KEY` بگذارید. کد آن را با هدر `Api-Key` به `https://api.neshan.org/v4/direction` می‌فرستد.
4. اختیاری: `NESHAN_DIRECTION_TYPE` (`car|walk|transit|bicycle`)، `NESHAN_DIRECTION_URL`، `NESHAN_TIMEOUT_MS` (پیش‌فرض ۳۵۰۰).

مسیرهایی که از آن استفاده می‌کنند: `GET /api/v1/delivery/orders/:orderId/estimate` و برآورد مسافت/زمان در `GET /api/v1/delivery/orders/:orderId/tracking`. اگر کلید نباشد یا نشان جواب ندهد، سرویس به haversine×۱٫۳۵ برمی‌گردد و همان را با `source: "ESTIMATED"` برچسب می‌زند — هیچ‌وقت عدد جعلی با برچسب واقعی نمی‌دهد.

### ۵-۲) `VITE_NESHAN_API_KEY` (مرورگر)

همان داشبورد، یک کلید دیگر با سرویس **Map SDK / Static** بسازید و در محدودیت کلید، **Referrer** را به دامنه‌های خودتان محدود کنید:

```
jetino-omega.vercel.app/*, localhost:5173/*
```

این کلید در `NeshanMapPicker` (انتخاب مختصات نشانی) استفاده می‌شود و چون در باندل مرورگر دیده می‌شود، محدودسازی دامنه اجباری است.

**نکتهٔ مهم:** نمایش موقعیت زندهٔ پیک به کلید مرورگر **وابسته نیست** — کارت پیگیری مسافت/زمان و لینک «مسیر روی نقشه» (`neshan.org/maps/@lat,lng`) را بدون کلید هم نشان می‌دهد. کلید فقط برای نشان‌دادن نقشهٔ درون‌صفحه‌ای در انتخابگر نشانی است.

**تست سرور:**

```bash
curl -s -H "Api-Key: $NESHAN_SERVER_KEY" \
  "https://api.neshan.org/v4/direction?type=car&origin=26.952,55.585&destination=26.96,55.60" | head -c 200
```

## ۶) Web Push (VAPID) — `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT`

بدون هیچ حساب بیرونی ساخته می‌شود:

```bash
npx web-push generate-vapid-keys
```

سه مقدار را در `.env` و Vercel بگذارید (`VAPID_SUBJECT` شکل `mailto:ops@example.com` دارد). کلید عمومی به مرورگر می‌رود (`GET /api/v1/notifications/push/public-key`)، کلید خصوصی فقط سرور است.

**تست:** از `/notifications` اشتراک را روشن کنید، سپس در پنل ادمین «اجرای صف» را بزنید؛ ردیف `PUSH` باید `SENT` شود. اگر `PUSH_NOT_CONFIGURED` ماند، متغیرها در محیط فعلی ثبت نشده‌اند.

**چرخش:** جفت کلید جدید بسازید؛ همهٔ اشتراک‌های قبلی باطل می‌شوند و کاربران باید دوباره اجازه بدهند.

## ۷) رمزهای خودساخته — `JWT_SECRET` و `OTP_HMAC_SECRET`

هیچ سرویسی لازم نیست؛ فقط دو رشتهٔ تصادفی و متفاوت:

```bash
openssl rand -hex 32   # JWT_SECRET
openssl rand -hex 32   # OTP_HMAC_SECRET
```

- `JWT_SECRET` (≥۳۲ نویسه): امضای توکن ۱۲ ساعته. تغییرش همهٔ نشست‌ها را قطع می‌کند.
- `OTP_HMAC_SECRET` (≥۳۲ نویسه): HMAC کد یک‌بارمصرف. تغییرش چالش‌های در جریان را باطل می‌کند.

هر دو باید در Vercel و `.env` یکی باشند؛ نبود یا کوتاه‌بودنشان ورود را با ۵۰۳ می‌بندد (fail-closed، نه fail-open).

## ۱۰) چک‌لیست ۱۰ دقیقه‌ای پیش از تحویل به مشتری واقعی

1. `DATABASE_URL` ست و `/api/v1/health` سبز است.
2. `JWT_SECRET` و `OTP_HMAC_SECRET` تصادفی و ≥۳۲ نویسه‌اند (نه مقادیر نمونه).
3. کاوه‌نگار: یک ورود واقعی با شمارهٔ خودتان انجام شد و پیامک رسید.
4. `JETINO_ALLOW_TEST_OTP` روی محیط واقعی **حذف** شده است.
5. `NESHAN_SERVER_KEY` ست است و `estimate` مقدار `source: "NESHAN"` می‌دهد.
6. `VITE_NESHAN_API_KEY` در پنل نشان به دامنه محدود شده است.
7. `CRON_SECRET` ست است و `dispatch` بدون هدر ۴۰۱ می‌دهد.
8. پیک آزمایشی: پروفایل کامل → ارسال کارت ملی و سلفی → تأیید در `/admin/settings` → تخصیص سفارش.
9. «کنترل تأیید مدارک پیک» را در `/admin/settings` روشن کنید و مطمئن شوید پیک تأییدنشده مأموریت نمی‌گیرد.
10. یک سفارش واقعی: اشتراک موقعیت پیک در مرورگر موبایل → کارت «موقعیت پیک» در `/orders` → دکمهٔ «درخواست کمک فوری» → دیدن آن در «گزارش‌های ایمنی» پنل ادمین.

## ۱۱) قواعد امنیتی کلیدها

- هیچ کلید سروری را در کد، README یا چت نگذارید؛ فقط `.env` (که در `.gitignore` است) و Vercel Environment Variables.
- کلیدهای مرورگر (`VITE_*`) را همیشه به دامنه محدود کنید؛ در غیر این صورت سهمیهٔ شما با یک کپی ساده مصرف می‌شود.
- هر کلید را جداگانه بچرخانید و بعد از چرخش Redeploy کنید.
- دسترسی داشبورد Vercel/Supabase/کاوه‌نگار/نشان را با ۲FA و حداقل تعداد عضو نگه دارید.

## ۱۰) زحل (zohal.io) — احراز هویت رسمی پیک

**چه چیزی می‌دهد:** سه سرویس که با هم هویت پیک را قطعی می‌کنند:

1. **شاهکار** (`POST /api/v0/services/inquiry/shahkar`) — آیا شمارهٔ موبایلی که پیک با آن وارد می‌شود به نام همان کد ملی است؟
2. **استعلام اطلاعات هویتی** (`POST /api/v0/services/inquiry/national_identity_inquiry`) — با کد ملی و تاریخ تولد، نام و نام خانوادگی ثبت‌احوال را برمی‌گرداند.
3. **احراز هویت بیومتریک** (`/api/v0/services/biometric/...`) — ویدئوی سلفی در سه قدم: `media/` (آپلود، `type=selfie_video`) → `session/liveness/` (شمارهٔ سریال کارت ملی، تاریخ تولد، جنسیت) → `session/{id}/result/` (نتیجه و دلیل).

**گرفتن کلید:**

1. در `https://dashboard.zohal.io/` ثبت‌نام کنید و دسترسی «شاهکار»، «استعلام اطلاعات هویتی» و «احراز هویت ویدیویی» را بگیرید.
2. توکن هر سرویس را از پنل بردارید. بیومتریک معمولاً **توکن جدا** دارد.
3. کلیدها را سروری نگه دارید: `ZOHAL_TOKEN` و `ZOHAL_BIOMETRIC_TOKEN` (اگر بیومتریک توکن جدا ندارد، همان `ZOHAL_TOKEN` کافی است).

**نکتهٔ حیاتی — IP ثابت:** زحل فقط از IPهای ثبت‌شده جواب می‌دهد. توابع Vercel IP خروجی ثابت ندارند؛ بنابراین یا باید بازهٔ IP خروجی را از پشتیبانی زحل ثبت کنید، یا استعلام را از یک سرویس با IP ثابت (پروکسی/VPS کوچک) رد کنید. بدون این، پاسخ `IP_NOT_ALLOWED` می‌گیرید و همان پیام فارسی به کاربر نشان داده می‌شود.

**محل ثبت:** `.env` محلی و `Vercel → Settings → Environment Variables` (Production/Preview) + Redeploy.

**تست:** با پیک وارد شوید، در `/driver` بخش «احراز هویت رسمی» را باز کنید؛ کد ملی/تاریخ تولد/سریال کارت را بدهید. پاسخ مورد انتظار در دیتابیس: `drivers.shahkar_matched=true`، `drivers.identity_matched=true` و بعد از ویدئو `biometric_status='MATCHED'`. هر فراخوانی در `identity_checks` ثبت می‌شود (نوع، نتیجه، کد خطا، تأخیر).

**هزینه:** هر استعلام در زحل حساب می‌شود؛ در کد هیچ درخواستی retry نمی‌شود و poll نتیجهٔ بیومتریک تا ۱۰ ثانیه بعد از هر سؤال، دوباره سؤال نمی‌کند.
