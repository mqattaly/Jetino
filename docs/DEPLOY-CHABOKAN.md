# دیپلوی جتینو روی چابکان

این سند کل مسیر بردن پروژه روی [چابکان](https://chabokan.net) را می‌گوید: یک سرویس
Docker که هم API و هم رابط کاربری را سرو می‌کند، به‌همراه یک دیتابیس PostgreSQL.

> **صادقانه:** شبکهٔ محیطی که این فایل‌ها در آن آماده شده به `chabokan.net` دسترسی ندارد،
> پس مراحل ساخت سرویس در پنل با مستندات عمومی چابکان نوشته شده و نه با کلیک واقعی روی
> پنل شما. خودِ تصویر Docker و رفتار تک‌سرویسی (سرو استاتیک، فالبک SPA، هدرهای کش،
> مایگریشن خودکار) محلی اجرا و تست شده است. اگر جایی از پنل با این متن فرق داشت،
> بگویید تا اصلاح کنم.

## چرا یک سرویس؟

فرانت‌اند در ۲۶ فایل، همهٔ درخواست‌ها را نسبت به `/api/v1` می‌فرستد. اگر UI و API روی
یک origin باشند:

- CORS لازم نیست (و `CORS_ORIGIN` خالی می‌ماند)،
- آدرس API در زمان build هاردکد نمی‌شود،
- service worker و PWA بدون دردسر روی همان دامنه کار می‌کند،
- یک دامنه، یک SSL، یک لاگ.

پس `Dockerfile` ریشه دو کار می‌کند: `dist` فرانت را می‌سازد و `api/dist` را؛ سپس یک
پروسهٔ Node هم `/api/v1/*` را جواب می‌دهد و هم صفحه‌های فرانت را.

## آنچه در ریپو آماده است

| فایل | کار |
|---|---|
| `Dockerfile` | build دو مرحله‌ای: نصب کامل → build فرانت و API → تصویر runtime سبک |
| `scripts/docker-entrypoint.sh` | اجرای مایگریشن‌ها (با تلاش مجدد) و بعد بالا آوردن سرور |
| `.dockerignore` | بیرون گذاشتن `node_modules`، `docs/`، `.env` و خروجی build از context |
| `api/src/config/database-url.ts` | خواندن `DATABASE_URL` یا ترکیب `DB_HOST`/`DB_PORT`/`DB_USER`/`DB_PASSWORD`/`DB_NAME` |
| `api/src/main.ts` | اگر `STATIC_DIR` ست باشد، UI را هم سرو می‌کند (فالبک SPA، هدر کش، `trust proxy`) |

## پیش‌نیازها

- حساب چابکان و یک پروژه
- دیتابیس **PostgreSQL ۱۶** (نسخهٔ ۱۶ چون مایگریشن‌ها روی همین تست شده‌اند)
- دسترسی چابکان به مخزن گیت‌هاب `mqattaly/Jetino` (اگر خصوصی است، integration گیت را وصل کنید)
- کلیدهایی که واقعاً دارید: کاوه‌نگار (پیامک ورود)، VAPID (پوش)، نشان (نقشه)

## گام ۱ — دیتابیس

۱. در پنل: **دیتابیس‌ها → ساخت دیتابیس → PostgreSQL** (نسخهٔ ۱۶).
۲. بعد از آماده شدن، مقادیر اتصال را بردارید: `Host`، `Port`، `Username`، `Password`،
   `Database name`. این‌ها را جایی امن نگه دارید؛ در چت نفرستید.

بعد در سرویس، دو راه برای معرفی دیتابیس دارید:

**راه الف (توصیه‌شده) — یک متغیر:**

```text
DATABASE_URL=postgresql://USER:PASSWORD@HOST:PORT/DBNAME
```

اگر رمز کاراکتر خاص دارد، آن را URL-encode کنید (`@` → `%40`، `#` → `%23`).

**راه ب — پنج متغیر جدا** (ساده‌تر برای کپی از پنل):

```text
DB_HOST=...
DB_PORT=5432
DB_USER=...
DB_PASSWORD=...
DB_NAME=...
# اگر اتصال از بیرون دیتابیس است و TLS اجباری دارد:
DB_SSL=1
```

> `PORT` را برای دیتابیس استفاده نکنید؛ همین نام در سرویس، پورت HTTP است و عمداً
> برای دیتابیس خوانده نمی‌شود.

## گام ۲ — ساخت سرویس

۱. **سرویس‌ها → ساخت سرویس جدید → Docker** (نه «هاست Node.js»؛ آن سرویس `npm start`
   را اجرا می‌کند و ما build دو مرحله‌ای Docker را می‌خواهیم).
۲. منبع کد: **مخزن گیت‌هاب** → `mqattaly/Jetino` → شاخه:
   - `arena/ef1f5812-jetino` (تا وقتی PR #1 باز و merge نشده)،
   - بعد از merge: `main`.
۳. نوع build: **Dockerfile**، مسیر: `Dockerfile` در ریشه (پیش‌فرض).
۴. پلن: حداقل **۱ گیگ رم** توصیه می‌شود. `npm ci` دو بار و `vite build` در زمان build
   حافظه می‌خواهد؛ روی ۵۱۲ مگ ممکن است build با OOM شکست بخورد.

اگر پنل «آرگومان‌های build» دارد و کلید عمومی نشان را دارید:

```text
VITE_NESHAN_API_KEY=<کلید عمومی نشان>
```

این تنها متغیری است که در **زمان build** لازم است (Vite آن را داخل باندل می‌گذارد)؛
بقیه در زمان اجرا خوانده می‌شوند. اگر ست نکنید، اپ سالم بالا می‌آید و فقط انتخاب
نقطه روی نقشه غیرفعال می‌شود (ورود دستی مختصات کار می‌کند).

## گام ۳ — پورت (مهم‌ترین نکتهٔ چابکان)

سرویس‌های Docker در چابکان به‌صورت پیش‌فرض روی **پورت ۸۰** باز می‌شوند، ولی برنامهٔ ما
روی `PORT=3000` گوش می‌دهد (در `Dockerfile` هم `EXPOSE 3000` است).

در بخش **پورت‌ها** (Ports) سرویس، پورت **3000** را با پروتکل HTTP ثبت کنید. اگر این را
جا بیندازید، همه‌چیز build می‌شود ولی دامنه ۵۰۲ می‌دهد.

## گام ۴ — متغیرهای محیطی

حداقل مجموعه برای بالا آمدن:

```text
PORT=3000
STATIC_DIR=/app/public
DATABASE_URL=postgresql://USER:PASSWORD@HOST:PORT/DBNAME
JWT_SECRET=<حداقل ۳۲ کاراکتر تصادفی>
OTP_HMAC_SECRET=<یک راز تصادفی دیگر، متفاوت>
CORS_ORIGIN=
```

ساخت رازها:

```bash
openssl rand -base64 48   # برای JWT_SECRET
openssl rand -base64 48   # برای OTP_HMAC_SECRET (باید متفاوت باشد)
```

بقیه، بسته به این‌که چه سرویسی فعال دارید:

| متغیر | بدون آن چه می‌شود |
|---|---|
| `KAVENEGAR_API_KEY` + `KAVENEGAR_OTP_TEMPLATE` | ورود با پیامک کار نمی‌کند (برای تست: `JETINO_ALLOW_TEST_OTP=1`، هرگز در تولید عمومی) |
| `VAPID_PUBLIC_KEY` + `VAPID_PRIVATE_KEY` + `VAPID_SUBJECT` | اعلان پوش ارسال نمی‌شود؛ ردیف‌ها `SKIPPED` می‌شوند، نه `SENT` جعلی |
| `CRON_SECRET` | مسیر `GET /api/v1/notifications/dispatch` بسته می‌ماند |
| `NESHAN_SERVER_KEY` | مسیر و زمان رسیدن محاسبه نمی‌شود؛ کرایه با نرخ ثابت |
| `ZOHAL_TOKEN` + `ZOHAL_BIOMETRIC_TOKEN` | احراز هویت رسمی پیک (شاهکار/ثبت احوال/بیومتریک) کار نمی‌کند |
| `DB_SSL` | فقط اگر دیتابیس TLS اجباری کند: `1` یعنی `require`؛ اگر گواهی self‑signed است `DB_SSL=no-verify` بدهید (مثل استخر Supabase) |
| `SKIP_MIGRATIONS=1` | فقط اگر خواستید مایگریشن خودکار خاموش شود (مثلاً هنگام دیباگ) |

> ⚠️ هیچ کلید واقعی را در ریپو یا `.env.example` نگذارید؛ فقط در متغیرهای محیطی سرویس.

## گام ۵ — دیپلوی و اولین بررسی

بعد از زدن دکمهٔ دیپلوی/ساخت، build حدود ۳ تا ۶ دقیقه طول می‌کشد (دو `npm ci` + build).

ترتیب رخدادها در لاگ سرویس باید این باشد:

```text
Applied migration 001_initial
...
Applied migration 026_zohal_driver_identity
Jetino API listening on :3000/api/v1 (+ UI)
```

اگر مایگریشن‌ها از قبل اعمال شده باشند، به‌جای `Applied` خط `Migration ... already applied`
می‌آید — این خطا نیست. اگر دیتابیس هنوز آماده نباشد، اسکریپت ورود تا ۱۰ بار با فاصلهٔ
۶ ثانیه تلاش می‌کند و بعد با خطای روشن متوقف می‌شود.

بررسی‌ها:

```bash
curl -s https://<your-domain>/api/v1/health
# {"status":"ok","service":"jetino-api","timestamp":"..."}

curl -sI https://<your-domain>/ | head -5           # باید ۲۰۰ text/html باشد
curl -sI https://<your-domain>/sw.js | head -5      # cache-control: no-store
curl -s https://<your-domain>/api/v1/nope           # ۴۰۴ JSON، نه HTML
```

در مرورگر: صفحهٔ اول باید بیاید (لوگو، جست‌وجو، پیشنهادها) و `/admin`, `/driver`,
`/grocery` هم باید صفحه را بدهند نه ۴۰۴.

## گام ۶ — اولین مدیر کل

سوپرادمین با کد ساخته نمی‌شود؛ باید یک کاربر واقعی را ارتقا بدهید:

۱. با شمارهٔ خودتان در اپ، ورود پیامکی را کامل کنید (اگر کاوه‌نگار ندارید، موقتاً
   `JETINO_ALLOW_TEST_OTP=1`, دیپلوی، ورود، و بعد خاموشش کنید).
۲. در کنسول/ترمینال سرویس (یا یک اجرای یک‌بارهٔ تصویر):

```bash
cd /app/api
ADMIN_PHONE=09123456789 node dist/database/promote-admin.js
```

۳. یک‌بار خارج و دوباره وارد شوید تا نقش در JWT بیاید؛ بعد `/admin` باز می‌شود.

## گام ۷ — دامنه و SSL

در بخش **دامنه‌ها** سرویس، دامنه (یا زیردامنهٔ چابکان) را وصل کنید و SSL را فعال بگذارید.
چند نکته:

- PWA و service worker فقط روی **HTTPS** نصب می‌شوند؛ دامنهٔ بدون SSL را برای تست موقت
  استفاده کنید، نه برای تحویل.
- اگر دامنهٔ اختصاصی دارید، رکورد `A`/`CNAME` را همان‌جا که چابکان می‌گوید ست کنید.
- `CORS_ORIGIN` را خالی بگذارید؛ فقط اگر UI را جای دیگری سرو کردید مقدار بدهید
  (چند دامنه با کاما).

## گام ۸ — زمان‌بند اعلان‌ها

روی Vercel این کار با cron انجام می‌شد. روی چابکان یکی از این دو:

- سرویس **Cron Job** چابکان (اگر در پلن شما هست) با فرمان HTTP روزانه:

  ```bash
  curl -fsS -H "Authorization: Bearer $CRON_SECRET" \
       "https://<your-domain>/api/v1/notifications/dispatch?limit=50"
  ```

- یا یک زمان‌بند بیرونی (cron سرور خودتان / سرویس رایگان) با همان درخواست.

بدون `CRON_SECRET` این مسیر بسته است و پوش‌های زمان‌بندی‌شده در صف می‌مانند.

## گام ۹ — بکاپ

۱. از پنل دیتابیس چابکان، بکاپ خودکار روزانه را فعال کنید (اگر پلن دارد).
۲. مستقل از آن، هفتگی یک `pg_dump` بگیرید و بیرون از سرویس نگه دارید:

   ```bash
   pg_dump "$DATABASE_URL" --no-owner --format=custom -f jetino-$(date +%F).dump
   ```

۳. تمرین بازیابی را یک‌بار روی یک دیتابیس خالی انجام دهید (`api/scripts/restore-drill.sh`).

## به‌روزرسانی نسخهٔ بعدی

- هر push به شاخهٔ وصل‌شده: در پنل دکمهٔ دیپلوی (یا webhook خودکار، اگر فعال کرده‌اید).
- مایگریشن‌های جدید در همان استارت به‌صورت خودکار اعمال می‌شوند.
- برای برگشت: تصویر نسخهٔ قبل را دوباره دیپلوی کنید؛ **مایگریشن‌ها برگشت‌پذیر نیستند**،
  پس قبل از دیپلوی تغییرات schema یک بکاپ بگیرید.
- اگر چند نمونه (instance) هم‌زمان بالا می‌آورید، مایگریشن خودکار را با
  `SKIP_MIGRATIONS=1` روی نمونه‌های اضافه خاموش کنید تا دو پروسه هم‌زمان مایگریشن نزنند.

## عیب‌یابی

| نشانه | علت محتمل | راه‌حل |
|---|---|---|
| build با OOM شکست می‌خورد | رم کم | پلن ۱ گیگ یا بیشتر |
| دامنه ۵۰۲ / پاسخ نمی‌دهد | پورت در بخش «پورت‌ها» ثبت نشده | پورت ۳۰۰۰ را ثبت کنید |
| `اتصال دیتابیس تنظیم نشده است` | نه `DATABASE_URL` نه `DB_*` | یکی از دو راه گام ۱ |
| `ECONNREFUSED` روی دیتابیس | دیتابیس داخلی است ولی از بیرون صدا می‌زنید، یا برعکس | از همان دسترسی‌ای استفاده کنید که پنل داده |
| `password authentication failed` | رمز URL-encode نشده | `@`, `#`, `%` را encode کنید |
| `self signed certificate` | `sslmode=require` در `pg` یعنی verify-full | `DB_SSL=no-verify` |
| صفحه سفید، API سالم | `STATIC_DIR` اشتباه | `/app/public` |
| `/sw.js` قدیمی در مرورگر | کش مرورگر | `Ctrl+Shift+R`؛ هدر `no-store` از سمت سرور تضمین شده |
| ورود پیامکی کد نمی‌فرستد | کاوه‌نگار تنظیم نشده | کلید + نام قالب، یا موقتاً `JETINO_ALLOW_TEST_OTP=1` |
| نقشه لود نمی‌شود | `VITE_NESHAN_API_KEY` در زمان build نبوده | آرگومان build و دیپلوی دوباره |

## تفاوت با دیپلوی فعلی روی Vercel

| موضوع | Vercel (فعلی) | چابکان |
|---|---|---|
| UI و API | دو build جدا در یک پروژه | یک کانتینر، یک origin |
| فایل ورودی API | `api-server.cjs` (سرورلس) | `api/dist/main.js` (long-running) |
| مایگریشن | در `npm install` (`scripts/vercel-build.cjs`) | در استارت کانتینر (`docker-entrypoint.sh`) |
| زمان‌بند | cron در `vercel.json` | سرویس Cron یا زمان‌بند بیرونی |
| `vercel.json` | لازم | بی‌استفاده (در `.dockerignore` هست) |

یعنی هر دو مسیر می‌توانند در کنار هم بمانند؛ اگر Vercel را نگه می‌دارید، این تغییرات
آن را نمی‌شکند (بدون `STATIC_DIR` همان رفتار قبل است و تست‌های API سبز مانده‌اند).
