# خرید از سوپرمارکت — مرحلهٔ ۱: لیست خرید متنی

این سند مدل کاری‌ای را ثبت می‌کند که برای فاز «سوپرمارکت» انتخاب شده، ساختار داده و API آن،
و آنچه در مرحلهٔ بعد اضافه می‌شود.

## ۱) مدل کاری (تصمیم‌های نهایی)

1. **مسیر اول این فاز:** مشتری به‌جای انتخاب قلم‌به‌قلم، یک **لیست متنی** می‌نویسد
   (مثلاً «۲ کیلو سیب، یک شانه تخم‌مرغ، نان سنگک»). سبد محصولات سوپرمارکت‌ها فاز بعد است.
2. **فروشگاه:** فعلاً متنی است؛ مشتری می‌تواند نام فروشگاه را بنویسد یا خالی بگذارد تا
   پیک خودش انتخاب کند. انتخاب از فهرست سوپرمارکت‌های ثبت‌شده بعد از ثبت‌نام آن‌ها می‌آید.
3. **هزینهٔ ماموریت:** مناقصهٔ ساده. همهٔ پیک‌های همان منطقه تا **۱۵ دقیقه** پیشنهاد می‌دهند،
   مشتری یکی را انتخاب می‌کند و بقیه رد می‌شوند.
4. **خرید و فاکتور:** پیک خرید می‌کند و فاکتور را ثبت می‌کند: مبلغ، **شمارهٔ کارت فروشگاه**
   و نام صاحب حساب، عکس فاکتور (اختیاری) و اقلام ریز (اختیاری؛ اگر ثبت شود جمعش باید با مبلغ
   فاکتور برابر باشد).
5. **کرایهٔ ماموریت پیش‌پرداخت است** (ضد سفارش فیک): بعد از قبول پیشنهاد، مشتری ۱۵ دقیقه وقت
   دارد کرایه را بپردازد و **تأیید آن با پشتیبانی/مدیر** است؛ تا تأیید نشود پیک نمی‌تواند
   «شروع خرید» بزند یا فاکتور ثبت کند.
6. **پرداخت کالا:** کارت‌به‌کارت **به حساب فروشگاه**؛ مشتری بعد از تأیید فاکتور، رسید را
   بارگذاری می‌کند و پیک (پس از پرسیدن از فروشنده) رسید را تأیید می‌کند. رسید بایگانی می‌ماند
   و پشتیبانی از هر دو رسید باخبر می‌شود.
7. **مهلت پرداخت کالا:** ۱۵ دقیقه بعد از تأیید فاکتور (`grocery_payment_minutes`).
8. **یادآوری و تمدید:** اگر مهلت (کرایه یا فاکتور) بگذرد، برای مشتری یک یادآوری می‌رود
   (dedupe روی اعلان) و پیک می‌تواند تا **۲ بار × ۱۵ دقیقه** تمدید کند
   (`grocery_extend_minutes` / `grocery_max_extensions`). ماموریت خودکار لغو نمی‌شود.
9. **اعتراض به فاکتور:** مشتری می‌تواند با دلیل فاکتور را رد کند؛ لیست به `SHOPPING` برمی‌گردد،
   پیک اصلاح می‌کند و دوباره می‌فرستد.
10. **استرداد:** اگر بعد از تأیید کرایه ماموریت لغو شود، مبلغ کرایه به **کیف پول** مشتری
   اضافه می‌شود (جدول `wallet_credits`، یک ردیف به‌ازای هر ماموریت).
11. **درگاه پرداخت:** هدف نهایی، پرداخت آنلاین هر دو بخش است. تا اتصال درگاه،
    `grocery_payment_mode='CARD_TO_CARD'` است؛ با `GATEWAY` شدن، درخواست کارت‌به‌کارت رد و
    مسیر آنلاین باز می‌شود (کلید درگاه هنوز وصل نیست).
12. **مدل درآمد:** از پنل مدیریت قابل انتخاب است (کلید `grocery_revenue_mode`):
    `NONE` (بدون کارمزد)، `FEE_PERCENT` (درصدی از هزینهٔ ماموریت)، `GOODS_PERCENT`
    (درصدی از مبلغ کالا)، `FIXED` (مبلغ ثابت). مقدار در لحظهٔ تأیید رسید کالا محاسبه و در
    `platform_fee_rial` ذخیره می‌شود.
13. **کارمزد از مشتری جدا گرفته نمی‌شود**؛ از سهم پیک/فروشگاه در تسویه کسر می‌شود.

## ۲) چرخهٔ وضعیت

```
OPEN ──(قبول پیشنهاد)──► ASSIGNED ──(شروع خرید)──► SHOPPING
  │                                                  │
  ├──(لغو مشتری)──► CANCELLED                        ├──(ثبت فاکتور)──► INVOICE_SENT
  └──(پایان مهلت)─► EXPIRED                          │                        │
                                                     │             (تأیید مشتری)▼
                                                     │                 AWAITING_PAYMENT
                                                     │                        │
                                                     │        (بارگذاری رسید)▼
                                                     │                      PAID
                                                     │                        │
                                                     │        (تأیید پیک)▼
                                                     └──────────── PAYMENT_CONFIRMED ──► DELIVERED
```

- لغو از طرف مشتری فقط در `OPEN`؛ بعد از آن لغو با دلیل از طرف پیک و با ثبت در
  `audit_logs` انجام می‌شود (و مشتری اعلان می‌گیرد).
- تحویل (`DELIVERED`) فقط بعد از تأیید پرداخت مجاز است.

## ۳) جدول‌ها (`021_grocery_lists`)

| جدول | نقش |
|---|---|
| `grocery_lists` | خود لیست: متن، فروشگاه، نشانی (اسنپ‌شات)، وضعیت، مهلت‌ها، فاکتور، پرداخت |
| `grocery_bids` | پیشنهاد هر پیک برای هر لیست (`UNIQUE(list_id, driver_id)`) |
| `grocery_invoice_items` | اقلام ریز فاکتور (اختیاری) |
| `grocery_stores` | فروشگاه: صاحب، منطقه، نام، تلفن، نشانی، وضعیت تأیید (`021` ندارد؛ `025`) |
| `grocery_products` | قفسهٔ فروشگاه: نام، دسته، واحد، قیمت ریالی، موجودی، عکس، فعال/بایگانی |
| `platform_settings` | کلیدهای `grocery_*` (مهلت‌ها و مدل درآمد) + ستون تازهٔ `value_text` |

## ۴) API

همهٔ مسیرها زیر `/api/v1/grocery` و پشت `JwtAuthGuard` هستند.

| متد | مسیر | چه کسی |
|---|---|---|
| `POST` | `lists` | مشتری — ثبت لیست (هدر `Idempotency-Key` اختیاری) |
| `GET` | `lists/mine` | مشتری — لیست‌های خودش + تعداد پیشنهادها |
| `GET` | `lists/:id` | مشتری/پیک همان ماموریت/کارکنان |
| `POST` | `lists/:id/bids` | پیک — ثبت یا ویرایش پیشنهاد |
| `POST` | `lists/:id/bids/:bidId/accept` | مشتری |
| `POST` | `lists/:id/invoice` | پیک ماموریت |
| `POST` | `lists/:id/invoice/approve` | مشتری |
| `POST` | `lists/:id/payment` | مشتری — رسید کارت‌به‌کارت |
| `POST` | `lists/:id/payment/confirm` | پیک ماموریت |
| `POST` | `lists/:id/status` | پیک — `SHOPPING` / `DELIVERED` / `CANCELLED` |
| `POST` | `lists/:id/cancel` | مشتری — فقط تا قبل از انتخاب پیک |
| `POST` | `lists/:id/fee-payment` | مشتری — رسید پیش‌پرداخت کرایه |
| `POST` | `lists/:id/invoice/reject` | مشتری — اعتراض به فاکتور با دلیل |
| `POST` | `lists/:id/deadline/extend` | پیک — تمدید مهلت `FEE` یا `PAYMENT` |
| `GET` | `board` | پیک — لیست‌های باز منطقه + ماموریت‌های خودش |
| `GET` | `admin/grocery/receipts` | کارکنان — صف رسید کرایه و رسید کالا |
| `POST` | `admin/grocery/lists/:id/fee/confirm` | کارکنان — تأیید کرایه |
| `GET` | `payment-destination` | مشتری — کارت/شبای مقصد پلتفرم + وضعیت درگاه (بدون AFK) |
| `GET`/`PATCH` | `admin/grocery/settings` | کارکنان — مدل درآمد، روش پرداخت، مهلت‌ها، کارت/شبا/صاحب حساب/بانک، کلید درگاه |
| `GET` | `admin/grocery/reports?from&to` | کارکنان — جمع کرایه/کالا/کارمزد، تفکیک مدل درآمد، روزانه، موارد نیازمند رسیدگی |
| `GET` | `admin/grocery/reports.csv?from&to` | کارکنان — همان بازه به‌صورت CSV (BOM دارد، ستون‌های فرمولی خنثی می‌شوند) |

قواعد سرور:

- مبلغ پیشنهاد بین ۱۰٬۰۰۰ و ۵۰٬۰۰۰٬۰۰۰ ریال؛ فاکتور حداکثر ۵۰۰٬۰۰۰٬۰۰۰ ریال.
- نقش‌های کارکنان برای این بخش: `SUPER_ADMIN`، `OPERATIONS_MANAGER`، `SUPPORT`.
- پیک باید `ACTIVE` باشد و اگر `require_driver_verification` روشن است، مدارک تأییدشده داشته باشد.
- پیک فقط لیست‌های منطقهٔ خودش را می‌بیند و به پیشنهاد پیک‌های دیگر دسترسی ندارد.
- رسید/فاکتور مثل بقیهٔ تصاویر اپ (حداکثر ۳۰۰KB، JPEG/PNG/WebP) اعتبارسنجی می‌شوند.
- هر تغییر وضعیت، اعلان + ردیف `audit_logs` دارد.

## ۵) پرداخت کارت‌به‌کارت و تنظیمات مقصد (مهاجرت `023`)

- کلیدهای `platform_settings`: `grocery_platform_card`، `grocery_platform_sheba`،
  `grocery_platform_holder`، `grocery_platform_bank`، `grocery_gateway_enabled`.
- **کارت‌به‌کارت هرگز خاموش نمی‌شود**؛ حتی وقتی روش پرداخت `GATEWAY` است، مشتری می‌تواند
  رسید کارت‌به‌کارت بفرستد. درگاه فقط یک مسیر اضافه است و با `grocery_gateway_enabled` روشن می‌شود.
- `value_text` در `platform_settings` حالا `NULL` می‌پذیرد تا «کارت تنظیم‌نشده» معنا داشته باشد.
- اعتبارسنجی: کارت ۱۶ رقم، شبا `^IR\d{24}$`، صاحب حساب ۳ تا ۱۲۰ نویسه، نام بانک ۲ تا ۸۰ نویسه.
- پاسخ `GET /grocery/payment-destination`:
  `{ fee: { cardToCard: { enabled, card, sheba, holder, bank, note }, online: { enabled, note } } }`.
  `enabled` کارت‌به‌کارت فقط وقتی `false` است که شمارهٔ کارت خالی باشد.
- `detail` هر لیست هم `paymentDestination` را برای مالک برمی‌گرداند تا صفحهٔ مشتری بدون
  درخواست دوم کارت را نشان دهد.

## ۶٫۵) پنل پیک — لیست‌های خرید

`src/DriverGrocery.tsx` بالای فهرست ماموریت‌های غذایی در `/driver` رندر می‌شود و از همان
اندپوینت‌های `/api/v1/grocery` استفاده می‌کند:

- **لیست‌های باز منطقه** از `GET grocery/board` (فقط لیست‌هایی که خودِ پیک روی آن‌ها پیشنهاد نداده)،
  با مهلت پیشنهاد، تعداد پیشنهادها، یادداشت و نشانی مشتری؛ فرم «پیشنهاد بده» مبلغ کرایه را
  به ریال می‌فرستد (`POST lists/:id/bids`).
- **پیشنهادهای در انتظار** (`board.myBids`) تا پیک بداند روی چه لیست‌هایی هنوز منتظر جواب است.
- **خریدهای در دست** با زنجیرهٔ دکمه‌ها: «شروع خرید» (`status=SHOPPING`، فقط بعد از
  تأیید کرایه) → «فرستادن فاکتور» (`POST invoice` با مبلغ، کارت و نام صاحب حساب فروشگاه و
  عکس فاکتور) → «مبلغ رو گرفتم» (`POST payment/confirm`) → «تحویل دادم»
  (`status=DELIVERED`). لغو ماموریت هم با دلیل (`status=CANCELLED`) در دسترس است و کرایهٔ
  تأییدشده را به کیف پول مشتری برمی‌گرداند.
- استایل‌ها: بخش ۲۷ در `src/next.css` (کلاس‌های `dg-*`).

## ۷) پنل ادمین — سوپرمارکت

`src/AdminGrocery.tsx` داخل صفحهٔ `/admin` («تنظیمات مالی») رندر می‌شود و شامل:

- مدل درآمد (بدون کارمزد / درصد کرایه / درصد کالا / مبلغ ثابت) با فیلد فعال برای هر مدل.
- کارت مقصد، شبا، صاحب حساب، بانک و کلید «درگاه متصل است» (کارت‌به‌کارت همیشه فعال می‌ماند).
- صف رسید کرایهٔ ماموریت با دکمهٔ «تأیید کرایه» (همان `POST admin/grocery/lists/:id/fee/confirm`).
- فهرست پرداخت‌های کالا با وضعیت تأیید پیک.

## ۷٫۵) گزارش‌ها (مرحلهٔ ۴)

- مهاجرت `024_grocery_revenue_snapshot` سه ستون `platform_fee_mode`، `platform_fee_bps` و
  `platform_fee_fixed_rial` را اضافه می‌کند؛ هنگام `payment/confirm` همراه با `platform_fee_rial`
  نوشته می‌شوند تا تغییر تنظیمات، گزارش‌های قدیمی را بازنویسی نکند. ماموریت‌های قبل از این
  مهاجرت در گزارش با کلید `UNSNAPSHOTTED` («بدون ثبت مدل») می‌آیند.
- `GET admin/grocery/reports` در یک رفت‌وبرگشت: `totals` (فقط پول تأییدشده)، `byModel`، `daily`،
  `attention` (۷ شاخص: رسید کالا/کرایهٔ منتظر، رسید کهنه، فاکتور کهنه، تحویل بدون پرداخت،
  لغو بدون استرداد، پرداخت بدون عکس رسید) و `queue` (۲۵ رسید در صف با موبایل مشتری).
- بازهٔ پیش‌فرض ۳۰ روز است، ورودی `YYYY-MM-DD`، بازهٔ معکوس/نامعتبر/بیش از ۴۰۰ روز رد می‌شود.
- رابط: `src/AdminGroceryReports.tsx` انتهای `AdminGrocery`؛ کارت‌های KPI، جدول مدل درآمد،
  فهرست رسیدگی، صف رسیدها، جدول روزبه‌روز (بازشو) و دکمهٔ «گرفتن CSV».
  استایل‌ها: بخش ۲۸ در `src/next.css` (کلاس‌های `report-*`).

## ۷٫۶) فروشگاه‌ها و قفسه (مرحلهٔ ۵)

- مهاجرت `025_grocery_stores`:
  - `grocery_stores(id, owner_user_id UNIQUE, region_id, name, phone, address_text, note, status
    PENDING|ACTIVE|SUSPENDED, approved_by, approved_at, created_at, updated_at)` — هر کاربر یک
    فروشگاه (یکتایی روی صاحب) و منطقه از `regions` فعال انتخاب می‌شود (فعلاً بندر خمیر).
  - `grocery_products(id, store_id, name, category, unit, price_rial, stock numeric(10,2),
    image_url, is_active, …)` با ایندکس یکتای `(store_id, lower(name))` تا اسم تکراری روی
    یک قفسه نباشد.
  - `grocery_lists.store_id` (nullable، `ON DELETE SET NULL`): لیست‌های قدیمی با `store_name`
    متنی و `store_id=NULL` کار می‌کنند؛ لیست تازه می‌تواند به فروشگاه واقعی وصل شود.
- قواعد:
  - ثبت فروشگاه فقط از طرف صاحبش (`POST grocery/store/mine`)؛ ویرایش، وضعیت را برنمی‌گرداند.
  - `PENDING` می‌تواند قفسه بچیند ولی در فهرست مشتری نمی‌آید؛ `SUSPENDED` نمی‌تواند کالا
    اضافه/ویرایش کند؛ `ACTIVE` تنها وضعیتی است که `GET grocery/stores` برمی‌گرداند.
  - هیچ کالایی حذف فیزیکی نمی‌شود؛ «برداشتن از قفسه» یعنی `is_active=false` تا فاکتورهای
    قبلی سالم بمانند.
  - قیمت قفسه فقط راهنمای مشتری است؛ مبلغ نهایی همان فاکتور فروشگاه است که پیک آپلود می‌کند
    (مدل درآمد و کرایهٔ ماموریت دست‌نخورده مانده است).
  - در `POST grocery/lists`، اگر `storeId` بیاید: فروشگاه باید `ACTIVE` و در همان منطقهٔ
    نشانی باشد و `store_name` اسنپ‌شات از خود فروشگاه گرفته می‌شود (نه از بدنهٔ درخواست).
- API تازه (همه پشت `JwtAuthGuard`):

| متد | مسیر | چه کسی |
|---|---|---|
| `GET` | `grocery/stores` | مشتری — فروشگاه‌های فعال + تعداد کالا |
| `GET` | `grocery/stores/:id/products` | مشتری — قفسهٔ همان فروشگاه |
| `GET` | `grocery/store/mine` | صاحب فروشگاه — فروشگاه و همهٔ کالاها |
| `POST` | `grocery/store/mine` | ثبت/ویرایش فروشگاه (idempotent با `ON CONFLICT(owner_user_id)`) |
| `POST` | `grocery/store/mine/products` | کالای تازه |
| `PATCH` | `grocery/store/mine/products/:id` | ویرایش کالا (قیمت/موجودی/عکس/فعال) |
| `DELETE` | `grocery/store/mine/products/:id` | برداشتن از قفسه (بایگانی) |
| `GET` | `admin/grocery/stores?status=` | کارکنان — صف تأیید/فهرست فروشگاه‌ها |
| `POST` | `admin/grocery/stores/:id/status` | کارکنان — `ACTIVE`/`SUSPENDED`/`PENDING` + یادداشت |

  تغییر وضعیت در `audit_logs` ثبت و به صاحب فروشگاه اعلان (`GROCERY_STORE_STATUS`) می‌شود.
- رابط‌ها:
  - `src/GroceryStoreApp.tsx` روی `/grocery/store`: ورود با OTP، فرم ثبت فروشگاه، بنر وضعیت،
    فرم کالا (دسته، واحد، قیمت ریالی، موجودی، عکس) و فهرست قفسه با ویرایش/برداشتن.
  - `src/GroceryApp.tsx`: انتخاب فروشگاه از `GET grocery/stores` جای ورودی متنی؛ اگر هیچ
    فروشگاهی تأیید نشده باشد همان ورودی متنی می‌ماند (سازگاری کامل).
  - `src/AdminGroceryStores.tsx` داخل `/admin`: فیلتر وضعیت، کارت هر فروشگاه با صاحب/تلفن/
    نشانی، «تأیید فروشگاه»، «معلق کن»، «برگردون به بررسی» و یادداشت برای صاحب فروشگاه.
  - استایل‌ها: بخش ۲۹ در `src/next.css` (کلاس‌های `store-*` و `admin-store*`).
